# Этап 0. Прогресс начисляет сервер

Сейчас статистику, серию, историю дней и достижения записывает браузер пользователя, а правила
базы разрешают владельцу писать в свой профиль что угодно. Любой может из консоли браузера выдать
себе серию в 1000 дней или все достижения. Для этапов 2–4 (опыт, лутка, лиги) это недопустимо:
редкость и рейтинги ничего не стоят, если их можно нарисовать.

Цель этапа: всё, что потом станет наградой или местом в рейтинге, считает сервер; браузер только
сообщает, что тренировка прошла, и читает результат.

## Площадка

- **Сейчас — Netlify Functions** (сайт уже на Netlify; Admin SDK Firebase работает и на бесплатном
  тарифе Firebase). Тариф Firebase Blaze не нужен.
- **Позже — Cloud Functions**, когда будет Blaze. Поэтому логика живёт отдельно от площадки:
  - `server/core/` — чистые функции без сети и базы (что засчитать, как обновить серию, какие
    достижения открылись). Покрыты тестами.
  - `server/` — работа с базой через Admin SDK (транзакции).
  - `netlify/functions/*.ts` — тонкие обёртки: разобрать запрос, проверить токен, вызвать `server/`.
- Адрес для клиента — `/api/*` (перенаправление на `/.netlify/functions/*` в `public/_redirects` — Netlify применяет его раньше `netlify.toml`),
  чтобы при переезде на Cloud Functions клиент не менялся.

## Что остаётся в браузере

- **Карточки и интервалы повторения** (SRS) — личные данные; подделка вредит только самому человеку.
- Профиль: имя, фото, username (через транзакцию `claimUsername`), курсы, папки, принятие документов.

## Что переезжает на сервер

### `POST /api/session` — тренировка завершена

Запрос (тело JSON, заголовок `Authorization: Bearer <Firebase ID token>`):

```ts
{
  id: string;            // uuid тренировки, создаёт клиент — повторная отправка не засчитывается дважды
  kind: "flashcards" | "review" | "quiz" | "speed" | "survival" | "match";
  collectionIds: string[];
  cards: number;         // сколько карточек пройдено (для теста — вопросов)
  correct?: number;      // тест и игры
  allKnow?: boolean;     // флэшкарты: все карточки «Знаю»
  durationSec: number;
  timezone: string;      // IANA, например "Europe/Oslo"
}
```

Сервер:

1. Проверяет токен → `uid`. Ограничение частоты: не больше 6 тренировок в минуту.
2. Если тренировка с таким `id` уже записана — возвращает её прежний результат.
3. **Проверяет правдоподобие**:
   - `cards` не больше, чем карточек в указанных наборах (наборы читает сам);
   - не меньше ~1 секунды на карточку и не больше 4 часов на тренировку;
   - `correct ≤ cards`. Неправдоподобную тренировку отклоняет (422) и пишет в журнал.
4. В одной транзакции обновляет профиль:
   - **история дней** — ключ дня по часовому поясу пользователя (это заодно исправляет старый
     UTC-сдвиг: занятие после полуночи больше не уходит во «вчера»);
   - **серия** — текущая дневная логика, но в часовом поясе пользователя;
   - **статистика** — счётчики тренировок, тестов, идеальных тестов, времени;
   - **достижения** — та же логика, что сейчас (`src/utils/achievements.ts`), но «сова» и
     «жаворонок» считаются по часу в часовом поясе пользователя, а «возвращение» — по дате
     последнего занятия на сервере.
5. Записывает тренировку в `users/{uid}/sessions/{id}` — журнал. Он же понадобится для опыта и лиг.
6. Возвращает: `{ streak: { current, longest, extendedToday }, newAchievements, stats }`.
   Клиент показывает празднование серии и баннер достижения по этому ответу, а не по своим расчётам.

### `POST /api/achievements/check` — после изменения наборов

Достижения за число слов и наборов («Первые слова», «Библиотекарь»…) открываются не тренировкой,
а созданием наборов и слов. Сервер сам считает слова и наборы пользователя и открывает
достижения. Клиент вызывает этот адрес после создания набора, импорта и добавления слов.

### Очередь неотправленных тренировок

Если сеть пропала или сервер ответил ошибкой (сеть, 429, 5xx), тренировка сохраняется в `localStorage`
и отправляется при следующем запуске приложения. Повтор безопасен благодаря `id`.
Такая тренировка засчитывается днём доставки, а не днём, когда прошла: время клиента не
принимаем на веру — иначе им можно было бы «закрыть» пропущенные дни серии задним числом.

## Правила базы

Клиенту запрещено менять в профиле: `stats`, `currentStreak`, `longestStreak`, `lastStudyDate`,
`studyHistory`, `achievements`, `timezone` (а на следующих этапах — `xp`, предметы, лиги).
Создать профиль клиент может только с нулевыми значениями этих полей.
Журнал `sessions` клиент может только читать.
Наборы (`collections`) остаются полностью доступны владельцу.

## Порядок выкладки

Порядок важен: если сначала закрыть правила, у пользователей со старой (закэшированной) версией
приложения перестанут сохраняться тренировки.

1. Выложить функции и новую версию клиента. Клиент пишет прогресс только через `/api/session`.
2. Подождать, пока закэшированные версии обновятся (приложение обновляется само при следующем
   открытии; ждём около недели).
3. Закрыть правила базы (`firebase deploy --only firestore:rules`) — отдельно, после подтверждения.

## Ключ сервера

Функциям нужен служебный ключ Firebase (Project settings → Service accounts → Generate new private key).
Это полный доступ к базе: только в переменных окружения Netlify (область — Functions), никогда — в git
и в переписке. При утечке — отозвать в той же консоли.

У функций Netlify общий лимит переменных около 4 КБ, поэтому из ключа берём только нужные поля:
`FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY` (переносы строк — `\n`) и, при необходимости,
`FIREBASE_PROJECT_ID` (по умолчанию `kolo-sets`).

## Где что лежит

| Что | Где |
|-----|-----|
| Чистая логика начисления и её тесты | `server/core/session.ts`, `server/core/time.ts`, `*.test.ts` |
| Транзакции Admin SDK | `server/progress.ts`, `server/admin.ts`, `server/http.ts` |
| Функции Netlify | `netlify/functions/session.ts`, `netlify/functions/achievements.ts` (`/api/*` → `netlify.toml`) |
| Клиент: отправка, очередь | `src/api/progress.ts`, `DataContext.reportSession`, `components/session/useRoundReport.ts` |
| Правила и их тесты | `firestore.rules`, `firestore.rules.emu.test.ts` |
| Тесты функций на эмуляторе | `server/progress.emu.test.ts` |

Команды: `npm test` — чистая логика; `npm run test:emu` — функции и правила на эмуляторах Firebase
(нужна Java). Локальная разработка: `/api` проксируется на развёрнутые функции
(`KOLO_API_TARGET`, по умолчанию — рабочий сайт), см. `vite.config.ts`.

## Проверка

- Чистая логика (`server/core/`) — тесты на сценарии: первая тренировка, вторая в тот же день,
  следующий день, пропуск, полночь в разных часовых поясах, повторная отправка, неправдоподобные
  данные, каждое достижение.
- Функции целиком — локально на эмуляторах Firebase (Auth + Firestore) через `netlify dev`,
  рабочая база не затрагивается.
- Правила — тестами на эмуляторе: владелец не может поменять защищённые поля, может — остальные.
- После выкладки — тестовый адрес Netlify и QA-аккаунт.

## Лимиты

- Тренировка ≈ 1 чтение и 1 запись профиля, 1 запись журнала, 1–3 чтения наборов.
  Бесплатных квот Firestore (50 000 чтений и 20 000 записей в день) хватит на тысячи тренировок в день.
- Лимиты Netlify Functions на текущем тарифе проверить перед выкладкой.

## Вне этапа

- Опыт, недельные орбиты, щиты, лутка — этап 2 (считаются в той же транзакции `/api/session`).
- Рейтинг игры дня — игра спрятана; при возвращении её счёт тоже переедет на сервер.
- Старые значения статистики не проверяются — отличить честные от подделанных нельзя.
